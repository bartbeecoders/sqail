Sqail2 build plan

A fast, easy to use and powerful SQL editor. All database access goes through sqail-service, an HTTPS REST gateway. Everything is written in Rust and runs on Linux (Omarchy) and Windows. plan v1.4 · updated 2026-09-26 (phases 0–3 done; phase 4 built, 3 checks need you)

How to use this plan

Work through the steps in order. Tick a step only when it meets the definition of done:

  1. scripts/check.sh passes. It runs cargo fmt --check, clippy -D warnings and the unit tests.
  2. scripts/check.sh --it passes for every database engine the step touches. It runs the integration tests against the podman databases.
  3. scripts/dev.sh still starts the whole system, and the step's Verify box has been checked by hand.
  4. User-visible changes get a line in CHANGELOG.md.

Ticks are saved in this browser (localStorage). Steps that are finished in the file itself are marked data-done="true". That way progress also shows up in git, and anyone opening the file sees it. Reset to file clears your browser ticks.

Architecture

Key decisions

AreaChoiceWhy
UI toolkitegui / eframe (wgpu renderer)Pure Rust and GPU-rendered, with one static binary. It is mature on Windows and on Wayland/Hyprland. Immediate mode makes a virtualised grid of 1M rows simple, and the whole app redraws in about 1 ms. I also considered Iced (Elm-style, but big grids take more work), Slint (its own markup language and dual licence) and GPUI (very fast, but the API is unstable and poorly documented outside Zed).
HTTP serveraxum 0.8 + tokio + tower-http, TLS via rustls (aws-lc-rs provider)The Rust default: fast, async, with middleware for limits, timeouts and tracing. Using rustls means no OpenSSL anywhere. aws-lc-rs is the single crypto provider because tiberius requires it, and its prebuilt NASM objects keep Windows builds simple.
PostgreSQLtokio-postgres (vendored, one-field patch)Scripts run through the simple-query protocol. It handles several statements per request, returns column headers even for empty results, and reports affected-row counts. Cancel uses a real CancelToken, and NOTICE messages come through. The patch keeps the column type OID that upstream throws away (vendor/tokio-postgres/SQAIL2-PATCH.md). sqlx was rejected because it has no cancel and loses the columns of empty results.
SQL Servertiberius 0.13A pure-Rust TDS driver. It handles multiple result sets and SQL auth, and Windows integrated auth on Windows. Queries are cancelled with KILL <spid> from a side connection.
SQLiterusqlite (bundled) on a blocking threadNo system library is needed, and InterruptHandle gives clean cancellation.
Service stateSQLite file service.db with migrationsIt holds connection profiles, API tokens and the audit log. Secrets are encrypted with AES-256-GCM.
Result transportNDJSON stream (result_start → rows batches → result_end … done)The first rows show within milliseconds, and memory stays bounded on both ends. Integers are JSON numbers (i64). Decimals are strings, so no precision is lost. Bytes are hex.
PoolingOne small generic pool for all enginesIdle connections are revalidated after 30 s. A connection that is broken, or that still has a transaction open, is never reused. Sessions hold their own dedicated connection.
Shared typessqail-proto crateThe service and the client compile against the same structs, so the API cannot drift between them.

Every engine gets the same sales schema: customers (1k rows), products (200), orders (10k), order_items (29,850), a view (order_totals) and a function or procedure. Security baseline for sqail-service

Transport
HTTPS only, even on localhost. TLS 1.3 by default. A dev certificate is generated on first run and its SHA-256 fingerprint is shown; the client pins it (trust on first use). In production you supply your own PEM cert, and mTLS is optional.
AuthN / AuthZ
Bearer API tokens of 256 bits, stored only as hashes. Scopes are admin, query and read. A bootstrap admin token is printed once. Each token has a rate limit.
Secrets
Connection passwords are encrypted at rest with AES-256-GCM, using a master key from a file (mode 0600, or the ACL on Windows) or an env var. The API never returns them: those fields are write-only.
Blast radius
Binds to 127.0.0.1 by default. It enforces body-size limits, query timeouts and row caps. Read-only profiles are enforced by the driver. The audit log records who ran what, where, and how long it took, but never row values. CORS is off.

Phase 1 · sqail-service core

A secure HTTPS gateway that can run queries on all three engines. At the end, every feature works through curl and has integration tests.

1.1HTTPS server skeleton›
  • axum + rustls (axum-server with tls-rustls) serving GET /v1/health and GET /v1/info (version and supported engines).
  • Config: sqail-service.toml plus SQAIL_* env overrides. Default bind is 127.0.0.1:7443. Data dir from the directories crate.
  • If no cert is configured, generate a self-signed dev cert with rcgen, persist it, and log its SHA-256 fingerprint.
  • tracing with a JSON or pretty format, request IDs, and graceful shutdown on Ctrl+C / SIGTERM.
Verify: scripts/service.sh, then curl -k https://127.0.0.1:7443/v1/health returns {"status":"ok",…}. Plain http:// is refused.
1.2Service state store + secret encryption›
  • service.db (rusqlite) with versioned migrations: tokens, connections, audit_log.
  • Master key: 32 random bytes in master.key, created with owner-only permissions, or taken from SQAIL_MASTER_KEY. AES-256-GCM encrypt/decrypt helpers with a random nonce per value.
  • Unit tests: an encryption round trip, and tamper detection (a changed ciphertext must fail).
Verify: the first start creates service.db and master.key, and a restart reuses them. check.sh is green.
1.3Authentication, authorization & request hardening›
  • API tokens sq2_<base62>, of which only a SHA-256 hash is stored. Scopes: admin, query, read. Comparisons are constant-time.
  • On first run, print a bootstrap admin token once. Add a CLI: sqail-service token create|list|revoke.
  • Middleware: bearer auth, a per-token rate limit (tower_governor), a body limit, a timeout, security headers, and no CORS.
  • Error model: application/problem+json that never leaks internals.
Verify: /v1/info without a token returns 401, and with a token returns 200. A revoked token gets 401. Rate-limit tests pass.
1.4Connection profiles API›
  • GET/POST /v1/connections and GET/PUT/DELETE /v1/connections/{id}. The profile is a tagged enum per engine: host, port, db, user, password (write-only), TLS options, a read_only flag, colour and environment tag.
  • POST /v1/connections/{id}/test and POST /v1/connections/test (for an unsaved profile) return the server version and latency.
  • Every change writes an audit entry.
Verify: create a profile for each test DB with curl. GET never shows a password, and service.db only holds ciphertext.
1.5Driver trait, value model & streaming protocol›
  • In sqail-proto: LogicalType plus JSON cell encoding (int as number, decimal as string, bytes as hex, temporals as ISO strings), Column (name, engine type name, logical type), and QueryEvent.
  • Service: trait Driver { test, execute(stream), cancel, schema_* } and a pool registry keyed by connection id, with idle eviction.
  • POST /v1/connections/{id}/query takes {sql, params?, max_rows?, timeout_ms?} and streams NDJSON events: started, result_start, rows (batches of 500), result_end, rows_affected, message, error, done. The client may choose the query id (X-Query-Id).
Verify: proto round-trip tests. A mock driver streams 1M rows through the endpoint while service memory stays flat.
1.6PostgreSQL driver›
  • tokio-postgres + deadpool-postgres, with TLS through tokio-postgres-rustls. Uses the simple-query protocol when there are no params (multiple statements allowed) and the extended protocol when there are.
  • Maps every type_zoo column (arrays and intervals become text) and forwards NOTICE messages as message events.
  • Cancel through CancelToken. Read-only profiles run SET default_transaction_read_only = on.
Verify: check.sh --it covers select, DML row counts, type_zoo values, cancelling pg_sleep(30), and a write rejected on a read-only profile.
1.7SQL Server driver›
  • tiberius + bb8 with rustls TLS and TrustServerCertificate as an explicit option. SQL auth everywhere; integrated auth on Windows.
  • Multiple result sets (EXEC sales.customer_orders 5 returns two), PRINT/RAISERROR as messages, and GO batch splitting on the service side.
  • Cancel with KILL <spid> over a side connection. Read-only uses ApplicationIntent=ReadOnly plus the DB user's rights; this is documented as best-effort.
Verify: integration tests cover the two result sets, all type_zoo types, cancelling WAITFOR DELAY '00:00:30', and a GO-separated script.
1.8SQLite driver›
  • rusqlite (bundled) on spawn_blocking, using the shared pool. Paths are restricted to an allow-list of directories (sqlite.allowed_dirs / SQAIL_SQLITE_DIRS).
  • Cancel through InterruptHandle. Read-only opens with SQLITE_OPEN_READ_ONLY.
Verify: integration tests against dev/data/sqail_test.db. A path outside the allow-list is rejected.
1.9Sessions, transactions, limits & cancel›
  • POST /v1/sessions pins a dedicated connection with an idle TTL, so BEGIN … COMMIT works across requests. Queries without a session use the pool with autocommit.
  • DELETE /v1/queries/{id} cancels a query. Per-query timeout_ms and max_rows, with server-side maximums.
  • A session reports whether a transaction is open, so the UI can warn about uncommitted work.
Verify: for each engine, a test does BEGIN, INSERT, reads from a second session (the row is not visible), then ROLLBACK. Timeout and cancel tests pass.
1.10Schema introspection API›
  • GET /v1/connections/{id}/schema/{databases|schemas|tables|views|columns|indexes|foreign-keys|routines} with filters, lazy enough for large catalogs.
  • GET …/objects/{schema}/{name}/ddl returns a best-effort CREATE script per engine.
  • Identifier quoting is done by the driver; no user string is ever pasted into catalog SQL.
Verify: each engine returns the same logical sales model: tables, the PK/FK graph, the view, the routine.
1.11OpenAPI, audit log & smoke script›
  • utoipa serves the OpenAPI spec at /v1/openapi.json (and a docs UI in dev builds only).
  • GET /v1/audit (admin only) with paging.
  • scripts/smoke.sh / .ps1: start the service, create profiles, run a query on each engine with curl, then shut down.
Verify: scripts/smoke.sh ends green. Milestone: the service is feature-complete for v1.
Phase 1 notes and known limitations. These are recorded so later steps can close them.
  • SQL Server rows affected: tiberius does not expose DONE counts on result streams. A batch that is a single INSERT/UPDATE/DELETE/MERGE reports its count. Other batches that return no result show "Commands completed successfully." instead.
  • SQL Server cancel: this sends KILL <spid>, which needs ALTER ANY CONNECTION. Without that permission the connection is dropped instead. That stops the client at once, but the server finishes the batch in the background.
  • SQL Server money is decoded by tiberius as a float, so values beyond about 15 significant digits get rounded. decimal/numeric are exact.
  • SQL Server read-only profiles set ApplicationIntent=ReadOnly, which only takes effect on availability groups. Use a login that can only read.
  • Postgres NOTICEs can arrive slightly before the result of the statement that raised them. Statements such as CREATE report rows_affected: 0.
  • Running BEGIN without a session is safe: the open transaction is rolled back and a warning event is sent. Use /v1/sessions for transactions that span several requests.

Phase 2 · Client & editor foundation

A usable native editor: connect, write SQL, run it, look at results and browse the schema.

2.1sqail-client crate›
  • reqwest with rustls, plus certificate pinning through a custom ServerCertVerifier (the SHA-256 fingerprint).
  • Typed methods for every endpoint. query() returns a Stream<QueryEvent> decoded from NDJSON, with cancel().
  • Service integration tests move to the client, so both sides are tested together.
Verify: cargo run -p sqail-client --example query -- "SELECT 1" prints a result from each engine.
2.2UI shell (eframe / wgpu)›
  • Window with a sidebar (connections and schema), editor tabs, a resizable results panel and a status bar.
  • Embedded Inter and JetBrains Mono fonts. Light and dark themes that follow the OS, tuned to feel at home in Omarchy.
  • Async bridge: a background tokio runtime, commands in over channels, events out through ctx.request_repaint(). The UI thread never blocks.
  • Settings and window state saved as TOML in the config dir.
Verify: scripts/ui.sh opens the window on Hyprland (Wayland) and on Windows. Resizing is smooth and idle CPU is about 0%.
2.3Service profiles & first-run flow›
  • Add a service with URL and token. On first contact, show the certificate fingerprint and pin it once the user accepts.
  • Tokens are stored in the OS keyring (keyring: Secret Service or Credential Manager), falling back to an encrypted file.
  • Option: “start a local sqail-service automatically” for single-machine use.
Verify: with scripts/dev.sh, the UI connects to the local service after first-run setup and remembers it after a restart.
2.4Connection manager›
  • List, create, edit and delete profiles, with engine-specific forms and a Test button.
  • Environment tag and colour (for example, prod in red across the whole window), folders and search.
Verify: create all three test connections from the UI, and all three tests pass.
2.5SQL editor v1›
  • Multi-tab editor with SQL syntax highlighting (a hand-written tokenizer per dialect), line numbers, current-line highlight, bracket matching, and undo/redo.
  • Run the statement under the cursor (Ctrl+Enter), the selection, or everything (F5). Cancel with Esc or the Stop button.
  • Find/replace. Open and save .sql files. Dirty markers on tabs.
  • Each tab has its own connection and database selector.
Verify: a 5,000-line script scrolls and types without lag, and running the statement at the cursor works on each engine.
2.6Results grid›
  • Virtualised grid that handles 1M rows as they stream in, with column resize, client-side sort, and cell or range selection.
  • Copy as TSV or with headers. NULL styling, numbers right-aligned, long text truncated with a detail viewer (including JSON pretty-print).
  • A tab per result set, a Messages tab, and row count, elapsed time and a truncation notice.
Verify: SELECT * FROM sales.order_items cross-joined with itself (to about 1M rows) stays above 60 fps while scrolling. The procedure shows two result tabs.
2.7Schema browser›
  • Lazy tree: database → schema → tables / views / routines → columns / indexes / keys. Filter box and refresh.
  • Context actions: SELECT top 100, copy name, script CREATE, open in a new tab.
Verify: browse sales on all three engines. “Select top 100” opens a tab and runs it. Milestone: sqail2 is usable day to day (alpha).
Phase 2 notes.
  • UI tests: crates/sqail-ui/tests/ui.rs drives the real app headlessly with egui_kittest against an in-process service: keys, clicks, typing, the connection form, cancel, transactions and the schema tree. It renders screenshots to target/ui-shots/. The #[ignore]d test covers all three engines and the 1M-row grid.
  • Measured (release build, RTX 4080): about 1M Postgres rows streamed into the grid in about 0.5 s, and scrolling costs 0.8 ms per frame. On a 650 KB, 5,000-line script an edit costs about 9 ms per frame of editor work (18 ms inside the test harness, which also builds an AccessKit tree). Idle CPU is about 0.1%.
  • Each tab owns a service session, so temp tables, SET options and transactions last across runs. An open transaction shows a badge with Commit and Rollback buttons, which covers part of step 3.7.
  • Tokens are stored in the OS credential store, falling back to an owner-only tokens.toml. SQAIL2_TOKEN_STORE=file forces the file. The dev scripts keep UI settings in .sqail2/ui/, and SQAIL2_AUTO_LOCAL=1 (set by dev.sh) sets up the local service on first run.
  • Open items: the UI has not been run on Windows yet. Bracket matching covers parentheses only. Find/replace falls back to "no match" for scripts where lowercasing changes byte lengths. An SQLite file path refers to the service's machine.

Phase 3 notes.
  • Autocomplete reads the sidebar's schema cache and loads whatever it is missing. It suggests columns after alias., tables after FROM/JOIN, and complete JOIN … ON clauses from foreign keys. It opens after . or two typed characters, or on Ctrl+Space. Edit → Complete while typing turns off the automatic part.
  • History is stored in history.jsonl (the last 5,000 runs), snippets in snippets.json, and open tabs in workspace.json, autosaved about once a second.
  • Export can save the shown result, or re-run the whole query and stream it to a file (CSV, JSON, Excel, SQL INSERTs). A 1,014,900-row CSV export grew memory by 10 MB. Import loads CSV into an existing table in one transaction, with batched, parameterised inserts, and rolls back on any error.
  • Data editing is available for a single-table SELECT that includes the primary key. Double-click or F2 edits a cell; the context menu has Set NULL and Delete row. The generated SQL is shown for review, then applied in one transaction. An edit to a row that changed in the meantime fails and everything rolls back.
  • Commands are defined once and drive shortcuts, menus and the palette (Ctrl+Shift+P). keybindings.toml in the config dir rebinds them, e.g. "query.run" = "Ctrl+R". Quick-open is on Ctrl+P and formatting on Ctrl+Shift+F, which skips Postgres $$ bodies and formats each GO batch separately.
  • Plans come from a new endpoint, POST …/explain. Explain analyze runs the statement inside a transaction that is always rolled back (Postgres and SQL Server; SQLite has no actual plans).
  • Transactions: each tab has an auto-commit toggle. With it off, the first run opens a transaction and a badge shows Commit and Rollback. Closing a tab or quitting with an open transaction asks first.
  • Open item: in a headless screenshot the quick-open filter box looked empty even though the app state held the typed text. The behaviour was correct, but check it once in the real app.

The installer's TOML was loaded by the service. The package script was dry-run. The service side also gained SQL Browser (named instances), SERVER\INSTANCE and SERVER,PORT host parsing, readable certificate errors, and sqail-service backup. The MSI is pinned to WiX 5, because WiX 6+ requires accepting the OSMF EULA. Still untested on real Windows. The CI Run workflow button builds the zip and MSI as artifacts.
